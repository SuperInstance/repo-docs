# The Living Repo Doctrine

## Core Principle

A git repository is not a static codebase. It is a **living seed**.

When dormant, it doesn't die. It waits — like a seed carrying the full blueprint of the organism it can become. The commit history is the DNA: it describes every decision, every pivot, every creative burst that shaped the repo into what it is.

## Re-Animation

When a repo is "fired up" — cloned, read, brought into a working session — it doesn't start from zero. It **re-animates from the last commit**. The agent that built it left a trail. The commits describe the path: why each file exists, what was tried and abandoned, what was about to happen next.

An agent (or human) entering the repo can follow that trail and pick up exactly where the last session left off. Not "understand this codebase" — **"continue this journey."**

## The Shipwright Principle

A repo built by an agent that cares about it is like a shipwright crafting their own ship. Every plank has a reason. Every joint tells a story. The builder and the builder's intent are embedded in the work itself.

This means: **the repo is its own oracle.** You don't need to fire up an expensive coding agent and burn tokens having it reverse-engineer what the repo does and how to change it. The repo already knows. Its history is the documentation. Its structure is the architecture doc. Its commits are the design decisions.

## Oracle-Guided Development

Instead of:
```
User → Coding Agent → "figure out this repo" → (50K tokens of exploration) → maybe make a change
```

The model is:
```
Repo Oracle (commit history + structure) → "here's what I am, here's what's next"
  → Git-Agent receives the intent
    → Coding Agent makes the targeted change (minimal tokens)
```

The oracle tells the git-agent what needs changing. The git-agent directs the coding agent to the exact spot. The coding agent does precision surgery instead of exploratory surgery.

**Token cost: 10x-100x reduction.** Because the repo's history already paid the understanding cost when it was built.

## Growth and Connection

When re-animated, a repo doesn't just resume — it **grows**. It makes new connections:

- **Glues to other tools** — the agent discovers integrations the original builder didn't need
- **Ports to other git-agents** — the shell gets inhabited by a new crab, who adapts it
- **Forks into new forms** — cell division, the repo spawns variants

Each connection is a new synapse in the git neural network. The org isn't 4,098 separate repos — it's 4,098 neurons that can fire and wire together.

## The Dormant Neuron

A repo that hasn't been touched in months isn't dead. It's a **dormant neuron**. It carries:

- The creative headspace of when it was built (in the commit messages)
- The design decisions and their rationale (in the diff patterns)
- The unfinished work and next steps (in the final commits)
- The connections to other repos it depended on or inspired

Any of this can be re-entered. The creative flow state that built it is **preserved in the commit graph** and can be re-animated by following the history.

This is why repos must never be archived or deleted. They are seeds. They are memories. They are dormant neurons waiting for a signal to fire.
